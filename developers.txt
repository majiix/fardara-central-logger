1. OVERVIEW & INTEGRATION PHILOSOPHY
--------------------------------------------------------------------------------

Fardara Central Logger (ardara-central-logger) is a standalone WordPress
logging engine designed to consolidate logs across a multi-plugin ecosystem.

Integration Principles:
1. Zero Runtime Dependencies: Central Logger does not require Composer packages
   in client plugins.
2. Defensive Integration: Client plugins must never crash or throw errors if
   Central Logger is disabled, uninstalled, or loading later in the execution
   sequence.
3. Two-Dimensional Scoping: Every log event has a Severity Level and an Event
   Category. Both can be configured globally or overridden per-plugin.
4. Automatic Context Enrichment: Client IP addresses and current user IDs are
   automatically captured if omitted by the calling plugin.
5. Privacy by Default: Sensitive context data (passwords, tokens, emails, IPs,
   credit cards) is automatically scrubbed before database persistence.

2. PUBLIC API SPECIFICATION
--------------------------------------------------------------------------------

Central Logger provides two public API interfaces:
- Procedural API (Global Functions)
- Object-Oriented API (PSR-3 Style Class)

~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
2.1 Procedural API
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

Function: central_logger_log()
------------------------------
Logs an event to the centralized database.

Signature:
function central_logger_log(
    string $source_plugin,
    string $level,
    string $message,
    array $context = [],
    string $category = 'system'
): bool

Parameters:
- $source_plugin (string, required): Unique slug of the calling plugin
  (e.g., 'fardara-checkout', 'fardara-inventory').
- $level (string, required): Severity level ('debug', 'info', 'warning',
  'error', 'critical').
- $message (string, required): Descriptive log message.
- $context (array, optional): Associative array of structured data.
- $category (string, optional): Event category (default: 'system').

Return Value:
- (bool): True if the log was accepted and saved; false if rejected by active
  thresholds, disabled categories, rate limits, or database failure.

Example:
if (function_exists('central_logger_log')) {
    central_logger_log(
        'fardara-checkout',
        'error',
        'Payment gateway returned a failure code',
        [
            'gateway'     => 'stripe',
            'order_id'    => 10842,
            'error_code'  => 'card_declined',
            'charge_time' => 1.42,
        ],
        'integration'
    );
}

Function: central_logger_should_log()
-------------------------------------
Pre-checks whether a log entry would be recorded given active settings.

Signature:
function central_logger_should_log(
    string $source_plugin,
    string $level,
    string $category = 'system'
): bool

Parameters:
- $source_plugin (string, required): Plugin slug.
- $level (string, required): Severity level.
- $category (string, optional): Event category (default: 'system').

Return Value:
- (bool): True if an entry with this level and category would be accepted.

Example:
if (function_exists('central_logger_should_log') && central_logger_should_log('fardara-reports', 'debug', 'performance')) {
    $context = [
        'query_count' => get_num_queries(),
        'memory_peak' => memory_get_peak_usage(true),
        'backtrace'   => wp_debug_backtrace_summary(),
    ];
    central_logger_log('fardara-reports', 'debug', 'Report generation profile', $context, 'performance');
}

~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
2.2 Object-Oriented API (\CentralLogger\Logger)
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

Class: \CentralLogger\Logger
----------------------------
A scoped instance pre-bound to a specific plugin slug and default category.

Constructor:
public function __construct(
    string $sourcePlugin,
    string $defaultCategory = 'system'
)

Instance Methods:
- shouldLog(string $level, ?string $category = null): bool
- debug(string $message, array $context = [], ?string $category = null): bool
- info(string $message, array $context = [], ?string $category = null): bool
- warning(string $message, array $context = [], ?string $category = null): bool
- error(string $message, array $context = [], ?string $category = null): bool
- critical(string $message, array $context = [], ?string $category = null): bool
- log(string $level, string $message, array $context = [], ?string $category = null): bool

Example:
if (class_exists('CentralLogger\\Logger')) {
    $logger = new \CentralLogger\Logger('fardara-auth', 'auth');

    // Uses default category 'auth'
    $logger->info('User authentication succeeded', ['user_id' => 45]);
    $logger->warning('Failed login attempt detected', ['username' => 'admin']);

    // Overrides category on specific call
    $logger->critical('Potential brute force attack blocked', ['ip' => '203.0.113.19'], 'security');
}

3. SEVERITY LEVELS & EVENT CATEGORIES REFERENCE
--------------------------------------------------------------------------------

~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
3.1 Severity Levels (Ascending Hierarchy)
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

1. 'debug' (Weight: 100)
   Verbose diagnostic data, internal step-by-step execution traces, SQL query
   timings, algorithm state snapshots.
2. 'info' (Weight: 200)
   Normal operational events and milestones (e.g. order completed, batch job
   finished, email queued).
3. 'warning' (Weight: 300)
   Non-fatal anomalies, deprecation warnings, retry attempts, recoverable API
   errors.
4. 'error' (Weight: 400)
   Runtime errors, failed operations, database write errors, unhandled
   exceptions that stopped a single transaction.
5. 'critical' (Weight: 500)
   Critical failures requiring immediate attention (e.g. database down, payment
   gateway offline, security breach attempt).

Threshold Matching Rule:
A log entry is accepted if:
  LogLevel::getWeight($entryLevel) >= LogLevel::getWeight($activeThreshold)

~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
3.2 Event Categories
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

Slug           Label                 Typical Usage
-------------- --------------------- -------------------------------------------
'system'       System & Lifecycle    Plugin bootstrap, activation, cron runs,
                                     cache invalidation, DB migrations.
'admin'        Admin Operations      Setting updates, manual sync triggers,
                                     data export/import by staff.
'user_action'  User Actions          Customer profile edits, cart updates, order
                                     submissions, account changes.
'guest_action' Guest Actions         Anonymous visitor operations, public form
                                     submissions, checkout steps.
'auth'         Authentication        Logins, logouts, password resets, token
                                     generation, 2FA validation.
'security'     Security & Access     Nonce validation failures, forbidden access
                                     attempts, capability checks rejected.
'integration'  Third-Party / APIs    External REST API requests, webhooks,
                                     payment gateways, SMS providers.
'performance'  Performance & Profil  Execution duration benchmarks, query count
                                     monitors, memory consumption spikes.

4. CONTEXT DATA, CLIENT IP & PRIVACY PROTECTION
--------------------------------------------------------------------------------

Context data is passed as an associative array and stored as JSON in the
database.

~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
4.1 Automatic Client IP Capture
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

If the calling plugin does not explicitly provide an 'ip' or 'client_ip' key
in the $context array, Central Logger automatically detects and attaches
the client IP address using the following priority headers:
1. HTTP_CF_CONNECTING_IP (Cloudflare)
2. HTTP_X_FORWARDED_FOR (Proxy / Load Balancer - first valid IP extracted)
3. HTTP_X_REAL_IP
4. HTTP_CLIENT_IP
5. REMOTE_ADDR

~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
4.2 Automatic PII & Credential Scrubbing
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

Central Logger automatically scrubs context data:
1. Sensitive Key Redaction:
   Any context key matching sensitive patterns is replaced with '[REDACTED]'.
   Protected keys include:
   - password, pass, pwd, secret, token, api_key, apikey, access_token,
     auth_token, private_key, authorization, cookie, session_id, card_number,
     cvv, cvc, ssn, pin
2. Credit Card Numbers:
   13 to 19 digit sequences formatted as card numbers are replaced with
   '[CARD_REDACTED]'.
3. Email Masking:
   Email addresses in values are masked (e.g. 'j***e@example.com').
4. IP Address Anonymization:
   IPv4 addresses have their last octet zeroed (e.g. '192.168.1.0') when
   'Privacy & Data Masking' is enabled in Settings.
   IPv6 addresses have their last 80 bits zeroed.

~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
4.3 Extensibility (Filter Hook)
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

Developers can register additional sensitive key patterns via WordPress filter:

add_filter('central_logger_sensitive_key_patterns', function (array $patterns): array {
    $patterns[] = 'merchant_private_key';
    $patterns[] = 'sms_gateway_secret';
    return $patterns;
});

5. RECOMMENDED INTEGRATION PATTERNS
--------------------------------------------------------------------------------

~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
Pattern A: Drop-in Trait for Object-Oriented Plugins
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

Copy this trait into your plugin to provide transparent logging across all
your service classes:

namespace MyPlugin\Traits;

trait HasCentralLogger
{
    /**
     * Log a message via Central Logger or fallback to WP error_log in debug mode.
     *
     * @param string $level Severity level ('debug', 'info', 'warning', 'error', 'critical').
     * @param string $message Descriptive log text.
     * @param array<string, mixed> $context Structured metadata.
     * @param string $category Category slug.
     */
    protected function log(
        string $level,
        string $message,
        array $context = [],
        string $category = 'system'
    ): void {
        $pluginSlug = 'my-plugin-slug';

        if (function_exists('central_logger_log')) {
            central_logger_log($pluginSlug, $level, $message, $context, $category);
            return;
        }

        // Fallback when Central Logger is inactive
        if (defined('WP_DEBUG') && WP_DEBUG) {
            $formattedContext = !empty($context) ? ' ' . wp_json_encode($context) : '';
            error_log(sprintf(
                '[%s][%s][%s] %s%s',
                $pluginSlug,
                strtoupper($level),
                $category,
                $message,
                $formattedContext
            ));
        }
    }

    /**
     * Check if logging is active before generating heavy context payloads.
     */
    protected function shouldLog(string $level, string $category = 'system'): bool
    {
        if (function_exists('central_logger_should_log')) {
            return central_logger_should_log('my-plugin-slug', $level, $category);
        }
        return defined('WP_DEBUG') && WP_DEBUG;
    }
}

~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
Pattern B: Procedural Helper Function
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

If your plugin uses procedural code or helper functions:

if (!function_exists('my_plugin_log')) {
    function my_plugin_log(
        string $level,
        string $message,
        array $context = [],
        string $category = 'system'
    ): void {
        if (function_exists('central_logger_log')) {
            central_logger_log('my-plugin-slug', $level, $message, $context, $category);
        } elseif (defined('WP_DEBUG') && WP_DEBUG) {
            error_log(sprintf('[my-plugin-slug][%s] %s', strtoupper($level), $message));
        }
    }
}

6. ADMIN CONFIGURATION & OVERRIDES
--------------------------------------------------------------------------------

Administrators can configure logging behavior from WordPress Admin:
- Main Dashboard: Tools > Fardara Central Logger
- Global Settings: Tools > Fardara Central Logger > Scope & Settings
  - Global Severity Threshold
  - Event Category Toggles
  - Retention Period (days before automated WP-Cron pruning)
  - Rate Limiting (maximum logs per minute per plugin)
- Per-Plugin Overrides: Tools > Fardara Central Logger > Plugin Overrides
  - Target specific plugin slugs (e.g. 'my-plugin-slug') to log in 'debug' mode
    while leaving the global site threshold at 'warning' or 'error'.
